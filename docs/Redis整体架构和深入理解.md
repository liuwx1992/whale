## 0. 一句话定位

Redis 是一个**基于内存、单线程（核心命令）、K-V 型、高性能**的 NoSQL 数据库。核心用"内存存储 + IO 多路复用 + 单线程命令执行"换取极致性能与简单并发模型，再靠"持久化 + 主从复制 + 哨兵/集群"补足可靠性与扩展性。

---

## 1. 适用场景

| 维度 | 说明 |
|---|---|
| 适用 | 缓存、计数器、排行榜、分布式锁、消息队列（Stream/List）、限流、会话、地理位置 |
| 不适用 | 海量持久存储（内存贵）、强事务联表、大于内存的数据集 |
| 特性 | 内存级延迟、丰富数据结构、单线程命令原子、持久化可选、主从+集群高可用 |

典型场景：DB 缓存、热点数据、分布式锁（Redisson）、限流、秒杀库存、消息队列、排行榜（ZSet）、附近的人（Geo）。

## 2. 整体架构总览

```
              ┌────────────────────────────────────┐
              │           Client / SDK              │
              └────────────────┬───────────────────┘
                               │ RESP 协议(6379)
              ┌────────────────▼───────────────────┐
              │            Redis Server            │
              │  ┌──────────────────────────────┐  │
              │  │ IO 多路复用(epoll/kqueue)     │  │  <- 网络 IO
              │  │   ↓ 事件                     │  │
              │  │ 文件事件分派器                │  │
              │  │   ↓                          │  │
              │  │ 命令处理器(单线程串行执行)      │  │  <- 命令执行, 原子
              │  │   ↓                          │  │
              │  │ 全局哈希表(键->值对象)         │  │  <- 内存数据
              │  └──────────────────────────────┘  │
              │  ┌──────────────────────────────┐  │
              │  │ 后台线程: 持久化/删除/复制     │  │  <- 异步, 不阻塞命令
              │  └──────────────────────────────┘  │
              └──────┬───────────────┬───────────────┘
                     │               │
            ┌────────▼─────┐   ┌─────▼──────────┐
            │ RDB/AOF 持久化│   │ 主从复制/哨兵/集群│
            └──────────────┘   └────────────────┘
```

核心层（理解 Redis 性能的关键）：

| 层 | 职责 |
|---|---|
| **网络 IO 层** | epoll/kqueue 多路复用，单线程接收连接与读写（6.0 后网络 IO 多线程可选） |
| **事件分派层** | 文件事件分派器把就绪 socket 派给对应命令处理器 |
| **命令执行层** | **单线程串行**执行命令，天然原子，无锁 |
| **数据存储层** | 全局哈希表（dict），键→值对象，值有 5+ 种类型 |
| **后台层** | 持久化（bgsave/aof）、惰性/异步删除、复制同步，子进程/线程异步不阻塞主线程 |

## 3. 为什么 Redis 快

1. **纯内存**：数据在内存，读写纳秒级，无磁盘 IO。
2. **IO 多路复用**：单线程 epoll 同时处理大量连接，事件驱动，非阻塞。
3. **单线程命令执行**：无上下文切换、无锁竞争、原子。核心路径简单。
4. **高效数据结构**：SDS、跳表、压缩列表、字典等针对性优化。
5. **单线程避免锁**：无加锁解锁开销。

> 注意：6.0 引入**网络 IO 多线程**（读/写 socket 并行），但**命令执行仍单线程**。所以"Redis 单线程"指命令执行层。

## 4. 数据类型与底层结构（核心）

| 类型 | 常见用法 | 底层结构（演进） |
|---|---|---|
| **String** | 缓存/计数/分布式锁 | SDS（简单动态字符串），预分配+二进制安全 |
| **List** | 消息队列、栈 | quicklist（双链表 + ziplist 节点）/ 7.0 listpack |
| **Hash** | 对象 | ziplist / listpack + hashtable |
| **Set** | 去重、标签 | intset（纯整数）/ hashtable |
| **ZSet** | 排行榜、延迟队列 | ziplist/listpack + **skiplist + dict**（dict 查分，跳表范围） |
| **Stream** | 消息队列（带消费组） | radix tree + listpack |
| **Bitmap/Bitfield** | 布隆、签到 | String 位操作 |
| **Geo** | 附近的人 | Zset + GeoHash 编码 |

### 4.1 SDS 为什么不用 C 字符串

- O(1) 取长度（SDS 存 len）。
- 二进制安全（不靠 `\0` 判结束）。
- 预分配空间，减少扩容；惰性释放。
- 兼容部分 C 字符串函数。

### 4.2 跳表（ZSet 核心）

ZSet 同时维护 **dict（member→score）** 和 **skiplist（按 score+member 排序）**：
- 点查（取分）：dict O(1)。
- 范围（排行榜）：skiplist O(logN)。
- 为什么不用红黑树：跳表实现简单、范围遍历友好、并发友好（部分场景）、内存换简单。Redis 选跳表。

### 4.3 ziplist/listpack

小数据用**压缩列表**（连续内存）省内存、缓存友好。超过阈值（元素数/大小）转 hashtable/skiplist，避免大数据下 ziplist 的连锁更新开销。7.0 用 listpack 替代 ziplist 修复连锁更新。

## 5. 持久化

### 5.1 RDB（快照）

- 全量快照，二进制紧凑，**恢复快、体积小**，适合备份/灾难恢复。
- 触发：`save`（阻塞）/ `bgsave`（fork 子进程异步）/ 定时/ `shutdown`。
- 缺点：两次快照间数据可能丢。

### 5.2 AOF（追加日志）

- 记录每条写命令（append），**数据更全**，丢得少。
- 刷盘策略：`always`（每条 fsync 最安全慢）、`everysec`（默认，每秒 fsync，平衡）、`no`（交 OS）。
- AOF 重写：AOF 变大后，fork 子进程按当前内存状态重写一份精简 AOF（去冗余历史命令），bgrewriteaof。
- 缺点：体积大、恢复慢（重放命令）。

### 5.3 4.0 混合持久化

`aof-use-rdb-preamble`：AOF 重写时，**前半段用 RDB 二进制快照，后半段追加增量 AOF 命令**。兼顾 RDB 恢复快 + AOF 数据全。生产推荐开启。

### 5.4 fork 与 COW

bgsave/bgrewriteaof 都靠 **fork 子进程**，利用 **COW（Copy-On-Write）**：父子共享内存页，写时才复制。所以"重写时不阻塞命令"，但大内存 fork 慢、COW 拷贝多时仍可能阻塞/占内存。

### 5.5 选型

| | RDB | AOF |
|---|---|---|
| 数据安全 | 差（丢一段） | 好（丢≤1s） |
| 体积 | 小 | 大 |
| 恢复速度 | 快 | 慢 |
| 性能 | 低（fork+全量） | 中（追加写） |
| 适用 | 备份/容灾 | 数据敏感生产 |

生产常**混合**：RDB 备份 + AOF everysec + 混合持久化。

## 6. 内存管理与淘汰策略

### 6.1 过期策略

- **惰性删除**：访问时检查是否过期，过期才删。可能堆积过期 key。
- **定期删除**：每隔一段时间随机抽一批 key 检查过期删除。
- 两者结合。

### 6.2 淘汰策略（maxmemory）

当内存达上限，按策略淘汰：

| 策略 | 范围 | 算法 |
|---|---|---|
| `noeviction` | 不淘汰，写报错 | — |
| `allkeys-lru` | 全部 | 近似 LRU |
| `allkeys-lfu` | 全部 | LFU（4.0+） |
| `allkeys-random` | 全部 | 随机 |
| `volatile-lru` | 设了 expire 的 | LRU |
| `volatile-lfu` | 设 expire | LFU |
| `volatile-random` | 设 expire | 随机 |
| `volatile-ttl` | 设 expire | 优先淘汰快过期的 |

缓存场景常用 `allkeys-lru`/`allkeys-lfu`；混合存储用 `volatile-*`。

### 6.3 近似 LRU/LFU

为不增加每次访问的开销，Redis 用**采样近似**：淘汰时随机取 N 个 key（`maxmemory-samples`，默认 5），从中选最久未用/最少用的淘汰。调大 samples 提精度但增开销。

### 6.4 内存优化

- 用高效结构（小 Hash 用 ziplist/listpack）。
- 控制键数量，分桶。
- 设置合理 TTL。
- bigkey 拆分。
- `object encoding` 看底层结构优化。

## 7. 主从复制

```
Master  --(全量+增量)-->  Slave
```

### 7.1 全量同步

首次/断线太久：
1. Slave 发 `PSYNC`，Master 判断需全量。
2. Master `bgsave` 生成 RDB + 用缓冲区记新写命令。
3. 发 RDB 给 Slave，Slave 加载。
4. 发缓冲区命令给 Slave 重放。

### 7.2 增量同步

- Master 维护**复制积压缓冲区**（repl_backlog，环形）+ **offset**。
- Slave 断线重连，带 offset，Master 从 backlog 增量补发。
- backlog 没覆盖到（断太久）→ 退回全量。

### 7.3 全量 vs 增量

| | 全量 | 增量 |
|---|---|---|
| 触发 | 首次/offset 失效 | 短断线重连 |
| 开销 | 大（RDB+传输） | 小 |
| 数据 | 全 | 部分（backlog 内） |

### 7.4 主从特点

- **读写分离**：主写从读，提读吞吐。
- **默认异步复制**：主不等从，可能丢；性能优先。
- 从默认只读。复制是单向 Master→Slave。

## 8. 哨兵 Sentinel（高可用）

主从中 Master 挂了要人工切，哨兵**自动故障转移**。

- **监控**：哨兵集群持续探测 Master/Slave。
- **主观下线（SDOWN）**：单个哨兵认为 Master 不可达。
- **客观下线（ODOWN）**：过半哨兵同意 → 确认下线。
- **选举 leader 哨兵**（Raft）执行故障转移。
- **选新主**：选优先级最高/offset 最新/_runid 小的 Slave 提升为主。
- **通知**：通知 Client + 其他 Slave 跟新主。

Client 连哨兵拿主地址，故障转移后自动感知新主。

## 9. Cluster 集群（分布式扩展）

哨兵解决高可用但不解决**容量/写扩展**。Cluster 用**分片**解决。

### 9.1 数据分片：16384 槽

- Cluster 把键空间分 **16384 个槽（slot）**。
- 每个节点负责一部分槽。
- 路由：`slot = CRC16(key) % 16384`。
- 客户端缓存槽→节点映射，直连目标节点。

### 9.2 节点通信 Gossip

节点间 Gossip 协议交换集群状态（谁负责哪些槽、谁活谁死），最终一致。

### 9.3 故障转移

节点发现某 Master 不可达（主观→客观下线），它的 Slave 选举提升为新主，接管槽。

### 9.4 为什么 16384 槽

作者权衡：节点数上限（集群规模不会上千）、心跳包大小（16384/8=2KB）、CRC16 映射够。更多槽冗余且心跳包大。

### 9.5 限制

- 不支持跨槽的多键操作（除非 hash tag 同槽 `{tag}key`）。
- 不支持跨节点事务/选库（db 0）。
- 客户端需支持 Cluster 协议（MOVED/ASK 重定向）。

## 10. 缓存三大问题（高频）

### 10.1 缓存穿透

查询**不存在的数据**，缓存没有、DB 也没有，每次穿透到 DB。

解决：
- 缓存空值（`key → null`，短 TTL）。
- **布隆过滤器**前置过滤不存在的 key。
- 接口层校验非法 id。

### 10.2 缓存击穿

**热点 key 过期瞬间**，大量并发请求同时打到 DB。

解决：
- **互斥锁**（setnx）：只让一个线程查 DB 回填缓存，其他等待。
- 热点 key 永不过期 + 后台更新。
- 逻辑过期（存过期时间，过期后互斥更新）。

### 10.3 缓存雪崩

**大量 key 同时过期** 或 **Redis 宕机**，请求全打 DB。

解决：
- TTL 加随机扰动，避免同时过期。
- 多级缓存（本地+Redis）。
- 限流降级保护 DB。
- 高可用（哨兵/集群）防宕机。
- 预热。

## 11. 分布式锁（高频场景）

### 11.1 基础 setnx

```
SET key value NX PX 30000   // 不存在才设, 带 TTL
```
解锁用 Lua 脚本保证"判断值+删除"原子。

### 11.2 问题与演进

- 忘加 TTL → 宕机死锁。→ 加 PX。
- 解锁删错别人锁 → value 存唯一标识，Lua 校验删。
- 主从异步复制，主加锁后未同步就宕机，新主没锁 → **Redlock**（多节点过半数加锁）。
- 工业级用 **Redisson**：看门狗自动续期、可重入、公平锁、Redlock 支持。

### 11.3 Redlock

在 N（奇数）个独立 Master 上 `SET NX PX`，过半数成功 + 总耗时 < TTL 即获锁。争议（时钟漂移等），但对偶发失效可接受的场景够用；强一致需求用 ZK/etcd。

## 12. 其他高频特性

- **Pipeline**：批量打包命令，省 RTT，提吞吐。
- **事务（MULTI/EXEC）**：命令队列顺序执行，**不支持回滚**（某命令出错其余仍执行）。watch 乐观锁。
- **Lua 脚本**：原子执行多步，命令级原子。
- **Stream**：5.0 消息队列，消费组、ack、持久，比 List/PubSub 更可用。
- **发布订阅 PubSub**：消息不持久，离线丢。
- **6.0 多线程 IO**：网络读写多线程，命令仍单线程。

## 13. 性能与运维要点

| 关注点 | 做法 |
|---|---|
| 大 key | 拆分/用 hash，避免阻塞与网络 |
| 热 key | 本地缓存、分片副本打散 |
| 慢查询 | `slowlog`，避免 KEYS/复杂操作 |
| 持久化 | 生产混合（RDB+AOF everysec） |
| 内存 | 设 maxmemory + 合理淘汰（allkeys-lru/lfu） |
| fork | 大内存 fork 慢，单实例内存别过大（≤10G）或用多实例 |
| 复制 | backlog 调大减全量；写少场景全量风险 |
| 集群 | 单分片容量控制，hash tag 跨槽 |
| 缓存问题 | 穿透布隆/击穿互斥/雪崩随机TTL+限流 |
| 监控 | 内存/fork/延迟/键过期/淘汰 |

## 15. 一张图串起核心概念

```
快: 内存 + epoll 多路复用 + 单线程命令(原子) + 高效结构
存: 全局哈希表 -> 值对象(String/List/Hash/Set/ZSet/Stream/Geo/Bitmap)
   底层: SDS/跳表+dict/ziplist/listpack/intset, 小数据压缩大数据哈希
持久: RDB(快照快恢复) + AOF(追加全) + 混合(RDB头+AOF尾), fork+COW
过期: 惰性+定期; 淘汰: maxmemory + LRU/LFU 采样近似
复制: Master->Slave 全量(RDB+缓冲) + 增量(backlog offset), 异步
高可用: 哨兵(监控+客观下线+选主+故障转移)
扩展: Cluster 16384槽 CRC16, Gossip, MOVED/ASK, 故障转移
场景: 缓存(穿透/击穿/雪崩) + 分布式锁(Redisson/Redlock) + MQ(Stream) + 排行榜(ZSet)
```

记住这条链，就抓住 Redis 全部骨架：**内存单线程快、高效数据结构、RDB/AOF 持久、主从/哨兵/集群、缓存三大问题**。
