# 测试产品命名与复用方案

> **文档版本**: v1.0
> **创建日期**: 2026-08-28
> **编写人**: weixin.liu
> **关联文档**: [QAT双实现一致性验证设计方案](./QAT双实现一致性验证设计方案.md)、[定制化产品一致性验证流程规范](./定制化产品一致性验证流程规范.md)、[speed配置缓存更新流程](./speed配置缓存更新流程.md)

---

## 1. 方案目标

统一测试产品的命名后缀，去掉 PRE/DEV 等多后缀分类，降低维护复杂度。产品、研发、QA 的测试产品都用同一种后缀 `_QAT`，仅靠名字区分归属，靠 status 字段区分在岗/下线。

---

## 2. 命名规则

| 形态 | 命名 | status | 说明 |
|---|---|---|---|
| 正式产品 | `{客户名}Cust` | 1 | 线上交付、客户跑数、双实现比对基准 |
| QA 测试产品 | `{正式code}_QAT` | 1 | QA 配置，做双实现比对 |
| 研发测试产品 | `{正式code}_QAT` | 1 | 研发联调用，复用同一后缀 |
| 产品预跑数产品 | `{客户名}Cust` | 1 | 产品自用，跑数测试，复用正式 code |
| 下线产品 | 同上 | 0 | 不再使用，等复用 |

后缀只有一种：`_QAT`。正式产品无后缀。归属靠完整 code 名区分，不靠后缀种类。

`_QAT` 这三个字母字面是"QA Test"的意思，研发和产品也用这个后缀语义上略拧，但后缀的职责是技术判别符（区分正式/测试），不是所有权标签。线上已有 Etest 测试产品混放先例，后缀就是个约定，不影响技术行为。

---

## 3. status 字段的作用

`AlCustProductConfigBean.status`：0 停用，1 正常。

### 3.1 当前行为

cacheExchange 校验 status 合法值（0 或 1），status=0 的产品仍会被加载到 map。路由层 `ConfigurableCustProdCommand` 不检查 status，status=0 的产品仍可被调用。

即当前 status 字段**没有运行时下线效果**，仅作为数据字段存在。

### 3.2 本方案要求

要实现"下线产品不响应调用"，需要在路由层增加 status 检查。详见第 5 节落地改动点。

---

## 4. 复用规则

### 4.1 为什么复用

测试产品（尤其是 QA 的 `_QAT` 产品）不随需求数量增长。一个 QA 维护 1-2 个 QAT 产品，测完一个新产品后复用同一个测下一个。产品下线后复用其 code 槽位给下一个客户。

### 4.2 复用方式：改 code + name + 配置

复用时必须同时修改 code、name 和配置，不能只改 name 和配置：

| 字段 | 是否改 | 原因 |
|---|---|---|
| code | 是 | code 是缓存 key 和调用路由 key，不改 code 意味着不同时期同一 code 跑的是完全不同的客户逻辑，历史调用记录对不上账。复用时改 code 中的客户名段反映当前客户 |
| name | 是 | 展示名更新为当前客户 |
| 配置 | 是 | filter/distinct/fields/timeSlices/orgGroups 等全部按新产品需求重配 |

### 4.3 复用示例

```
第一轮：ApplyLoanAACust_QAT（客户A的测试产品）
  -> 测完，status 改 0 下线

第二轮：改 code 为 ApplyLoanBBCust_QAT（客户B），status 改 1，重配所有配置
  -> 复用同一个 code 槽位，测客户B
```

### 4.4 不保留历史快照

复用是覆盖，不是新建。旧配置不保留快照，speed 有版本记录可追溯历史。如果需要回溯旧客户配置，从 speed 的版本历史中取。

---

## 5. 落地改动点

| # | 改动点 | 说明 |
|---|---|---|
| 1 | code 命名校验 | cacheExchange 中增加校验：正式产品 code 禁止含 `_QAT`，测试产品 code 必须以 `_QAT` 结尾。当前无此校验 |
| 2 | status 运行时检查 | 路由层 ConfigurableCustProdCommand 增加检查：取到 bean 后如果 status=0 则拒绝调用（setFlag 98 或类似），返回"产品已下线" |

两项改动均为小幅增强，不涉及架构变更。

---

## 6. 方案优点

- 后缀只有一种 `_QAT`，命名规则简单，校验逻辑从多后缀缩减为一条
- 正式产品无后缀，和线上现有产品命名一致
- status 字段已存在，复用现有数据结构
- 产品池概念不变，只是池内产品靠 status 标记在岗/下线
- 测试产品数量可控，不随需求数增长

---

## 7. 风险与注意

### 7.1 归属区分靠名字，不靠后缀

后缀统一后，QA 和研发的测试产品都叫 `_QAT`，区分归属只能靠完整 code 名。命名时需保证不歧义，例如不同 QA 的产品可在 code 中带人名段：`ApplyLoanXXCust_Qa1_QAT`、`ApplyLoanXXCust_Qa2_QAT`。

### 7.2 status 运行时检查需落地

当前路由层不检查 status，status=0 的产品仍可被调用。要实现"下线即不响应"，必须在路由层加 status 检查。否则 status=0 的产品被复用时，旧调用方仍能调到新配置，造成数据错乱。

### 7.3 复用时改 code 的审计意义

复用必须改 code，不能只改 name+配置。如果 code 不变，同一 code 在不同时期跑不同客户逻辑，调用日志和 speed 版本记录虽然能追溯，但 code 层面看不出客户切换，增加排查成本。改 code 中客户名段是最低成本的审计清晰性保证。
