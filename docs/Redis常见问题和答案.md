## 一、基础与性能

### Q1. Redis 是什么？为什么快？

**要点速答**：内存型 K-V 数据库，单线程命令执行。快的原因：纯内存、epoll 多路复用、单线程无锁无切换、高效数据结构、避免锁。

---

### Q2. Redis 真的是单线程吗？

**要点速答**：**命令执行是单线程**，但 Redis 6.0 后**网络 IO 可多线程**（读/写 socket 并行）。后台还有子进程/线程做持久化、异步删除、关闭 fd 等。所以"单线程"指核心命令执行路径，不是全进程单线程。

---

### Q3. 单线程为什么还能高并发？

**要点速答**：基于内存（纳秒）+ epoll 事件驱动（一个线程处理上万连接）+ 命令简短不阻塞。关键是**所有命令不能慢**，否则一个慢命令拖垮整个实例——所以禁用 KEYS、复杂排序等。

---

### Q4. Redis 和 Memcached 区别？

**要点速答**：Redis 数据结构丰富（5+种）、持久化（RDB/AOF）、主从/哨兵/集群高可用、支持多种值操作。Memcached 只纯 K-V 内存、无持久、多线程。功能选 Redis，极致简单纯缓存选 Memcached。

---

## 二、数据类型与结构

### Q5. Redis 五大基础数据类型？

**要点速答**：String、List、Hash、Set、ZSet（Sorted Set）。后续加 Stream、Bitmap、Bitfield、Geo、HyperLogLog。

---

### Q6. ZSet 底层结构？为什么用跳表？

**要点速答**：ZSet 同时维护 **dict（member→score，点查 O(1)）** + **skiplist（按 score 排序，范围 O(logN)）**。跳表而非红黑树：实现简单、范围遍历友好、并发友好、内存可接受。详见架构文档 §4.2。

---

### Q7. SDS 为什么不用 C 字符串？

**要点速答**：SDS（简单动态字符串）O(1) 取长度、二进制安全（不靠 `\0`）、预分配省扩容、惰性释放、兼容部分 C 函数。

---

### Q8. Redis 的 Hash 底层什么时候用 ziplist/hashtable？

**要点速答**：元素少且单个值短时用 **ziplist/listpack**（连续内存，省内存、缓存友好）；超阈值（元素数/单值大小）转 **hashtable**。7.0 listpack 替代 ziplist 避免**连锁更新**。`object encoding key` 可查。

---

### Q9. String 存对象和 Hash 存对象优劣？

**要点速答**：
- String（JSON）：一次取整个对象，简单；但改一字段要整体重写，大 value 网络开销。
- Hash：字段级 get/set，省网络、可部分更新；但操作多。小 Hash 走 ziplist 省内存。频繁字段操作选 Hash，整体读写选 String。

---

### Q10. Redis 怎么实现计数器/限流？

**要点速答**：
- 计数器：`INCR`（原子）。
- 限流（固定窗口）：`INCR key` + `EXPIRE`。
- 滑动窗口限流：ZSet 存请求时间戳，`ZREMRANGEBYSCORE` 清旧 + `ZCARD` 计数判断。
- 令牌桶/漏桶可用 Lua 脚本原子实现。

## 三、持久化

### Q11. RDB 和 AOF 区别？怎么选？

**要点速答**：

| | RDB | AOF |
|---|---|---|
| 内容 | 全量快照二进制 | 命令追加日志 |
| 数据安全 | 丢一段 | 丢≤1s（everysec） |
| 体积 | 小 | 大 |
| 恢复 | 快 | 慢（重放） |
| 适用 | 备份/容灾 | 数据敏感生产 |

生产常混合：RDB 备份 + AOF everysec + 4.0 混合持久化。

---

### Q12. AOF 三种刷盘策略？

**要点速答**：
- `always`：每条写 fsync，最安全慢。
- `everysec`（默认）：每秒 fsync，平衡，最多丢 1s。
- `no`：交 OS 刷，性能高但可能丢多。

---

### Q13. AOF 重写是什么？为什么需要？

**要点速答**：AOF 不断追加会变大且含冗余历史命令。**重写**：fork 子进程按当前内存状态生成精简 AOF（如多次 INCR 合成一条 SET），减体积、提恢复速度。期间新写命令同时入旧 AOF 和缓冲区，重写完替换。

---

### Q14. bgsave/AOF 重写为什么用 fork？COW？

**要点速答**：fork 子进程在后台做持久化不阻塞主线程命令。**COW（Copy-On-Write）**：父子共享内存页，主线程写时才复制该页，子进程拿到的是某一时刻一致快照。代价：大内存 fork 慢、COW 拷贝多时占内存。

---

### Q15. 混合持久化是什么？

**要点速答**：4.0 `aof-use-rdb-preamble`，AOF 重写时**前半段写 RDB 二进制快照 + 后半段追加增量 AOF 命令**。兼顾 RDB 恢复快 + AOF 数据全，生产推荐。

---

## 四、内存与淘汰

### Q16. Redis 过期策略？

**要点速答**：**惰性删除**（访问时检查过期才删）+ **定期删除**（每隔随机抽 key 检查删除）结合。惰性可能堆积过期 key，定期扫描兜底。

---

### Q17. 内存淘汰策略有哪些？

**要点速答**：`noeviction`（不淘汰写报错）、`allkeys-lru/lfu/random`、`volatile-lru/lfu/random/ttl`（仅设 expire 的）。缓存常用 `allkeys-lru` 或 `allkeys-lfu`。

---

### Q18. LRU 和 LFU 区别？Redis 是精确 LRU 吗？

**要点速答**：LRU 最近最少使用（淘汰最久没访问），LFU 最少频率使用（淘汰访问次数少）。Redis 用**采样近似**（`maxmemory-samples` 默认 5，随机抽 N 个选淘汰），不是精确全量 LRU，省每次访问开销。

---

### Q19. 怎么发现和优化 bigkey？

**要点速答**：`redis-cli --bigkeys`、`memory usage key`。优化：拆分（大 hash/list 拆小）、用 hash 结构、设 TTL、异步删除（`UNLINK`）。bigkey 会阻塞（删除/序列化慢）、网络开销大、集群迁移慢。

---

## 五、主从与高可用

### Q20. Redis 主从复制原理？

**要点速答**：
- **全量**：Slave 发 PSYNC，Master bgsave 生成 RDB + 缓冲区记新写，发 RDB 给 Slave 加载 + 发缓冲区命令重放。
- **增量**：Master 维护 repl_backlog 环形缓冲 + offset，Slave 短断线带 offset 增量补发；offset 失效（断太久）退全量。
- 异步复制，主不等从。详见架构文档 §7。

---

### Q21. 全量复制和增量复制的触发？

**要点速答**：
- 全量：首次同步、Slave 重启/offset 不在 backlog、backlog 太小覆盖不到。
- 增量：短断线重连、offset 在 backlog 内。生产调大 `repl-backlog-size` 减少全量。

---

### Q22. 哨兵的作用和故障转移过程？

**要点速答**：哨兵集群监控 Master/Slave，自动故障转移：
1. **主观下线 SDOWN**：单哨兵判不可达。
2. **客观下线 ODOWN**：过半哨兵同意。
3. **选 leader 哨兵**（Raft）执行转移。
4. **选新主**：优先级/offset 最新/runid。
5. 通知 Client + 其他 Slave 跟新主。

---

### Q23. 主观下线和客观下线区别？

**要点速答**：主观下线是**单个哨兵**自己判断 Master 不可达（可能网络抖动）。客观下线是**过半哨兵**都同意，才确认真下线，触发故障转移。过半防误判。

---

## 六、集群分片

### Q24. Redis Cluster 怎么分片？

**要点速答**：把键空间分 **16384 槽**，每节点负责一部分。路由 `slot = CRC16(key) % 16384`。Client 缓存槽→节点映射直连目标节点。节点间 Gossip 通信维护集群状态。

---

### Q25. 为什么是 16384 个槽？

**要点速答**：作者权衡：集群节点数上限合理（不会上千节点）、心跳包大小（16384/8=2KB）、CRC16 映射足够。槽过多心跳包大无收益。

---

### Q26. Cluster 的 MOVED 和 ASK 重定向区别？

**要点速答**：
- **MOVED**：槽已迁移到新节点，永久重定向，Client 更新本地槽映射。
- **ASK**：槽正在迁移中，临时重定向到目标，Client 不更新映射（只这一次）。

---

### Q27. Redis Cluster 限制？

**要点速答**：不支持跨槽多键操作（除非 hash tag `{tag}` 同槽）、不支持跨节点事务/选库（只能 db 0）、需 Cluster 客户端处理重定向、Reshard 期间有性能影响。

---

### Q28. 哨兵和 Cluster 怎么选？

**要点速答**：哨兵解决**高可用**（Master 自动切换）但不解决容量/写扩展，适合单实例数据量不大。Cluster 解决**高可用 + 分片扩展**，适合数据量超单机内存、要写扩展。要扩展选 Cluster，单机够用选哨兵。

---

## 七、缓存三大问题

### Q29. 缓存穿透是什么？怎么解决？

**要点速答**：查**不存在的数据**，缓存和 DB 都没有，每次穿透 DB。解决：缓存空值（短 TTL）、**布隆过滤器**前置过滤、接口校验非法 id。

---

### Q30. 缓存击穿是什么？怎么解决？

**要点速答**：**热点 key 过期瞬间**，大量并发同时打 DB。解决：互斥锁（setnx 只让一个查 DB 回填）、热点 key 永不过期 + 后台更新、逻辑过期。

---

### Q31. 缓存雪崩是什么？怎么解决？

**要点速答**：**大量 key 同时过期**或 **Redis 宕机**，请求全打 DB。解决：TTL 加随机扰动避免同时过期、多级缓存、限流降级、高可用（哨兵/集群）、预热。

---

### Q32. 缓存和 DB 一致性怎么保证？

**要点速答**：
- **Cache Aside**（旁路）：先更 DB 后删缓存，读时回填。延迟双删防脏读。
- 强一致场景：先删缓存→更 DB→延迟再删（双删）；或订阅 binlog（Canal）异步刷缓存。
- 完全强一致要走 DB。多数场景接受最终一致。

---

## 八、分布式锁

### Q33. Redis 怎么实现分布式锁？

**要点速答**：`SET key value NX PX 30000`（不存在才设 + TTL 防死锁）。value 存唯一标识，解锁用 **Lua 脚本**保证"判断是自己的锁 + 删除"原子。工业级用 Redisson（看门狗续期、可重入、Redlock）。

---

### Q34. 分布式锁的常见问题和演进？

**要点速答**：
- 忘 TTL → 宕机死锁 → 加 PX。
- 删错别人锁 → value 唯一标识 + Lua 校验删。
- 主从异步复制主宕机丢锁 → **Redlock**（多 Master 过半数加锁）。
- 业务超时锁被释放 → 看门狗（Redisson）自动续期。

---

### Q35. Redlock 是什么？争议？

**要点速答**：在 N（奇数）个独立 Master 上 `SET NX PX`，过半数成功 + 总耗时 < TTL 即获锁。争议：依赖系统时钟、GC/网络暂停可能失效。对偶发失效可接受场景够用；强一致用 ZK/etcd（基于租约+fencing token 更稳）。

---

### Q36. Redisson 看门狗原理？

**要点速答**：Redisson 加锁后启**定时任务**（默认每 1/3 TTL 续期一次），只要客户端存活就持续续期，防止业务超时锁自动释放。客户端宕机则任务停，锁到 TTL 自动释放。可重入靠 hash 结构记重入次数。

## 九、事务/脚本/Pipeline

### Q37. Redis 事务（MULTI/EXEC）支持回滚吗？

**要点速答**：**不支持回滚**。MULTI 开启后命令入队，EXEC 顺序执行；某命令出错（语法错误）整队列不执行，但**运行时错误**（如类型不符）该条失败，其余仍执行，不回滚。设计哲学：错由程序员负责，避免回滚开销。

---

### Q38. WATCH 是什么？

**要点速答**：**乐观锁**。WATCH 一个 key，EXEC 前若该 key 被修改，整个事务**放弃**（返回 nil）。常用于"扣库存"等 check-and-set：WATCH stock → MULTI → DECR → EXEC，失败重试。

---

### Q39. Lua 脚本的作用？

**要点速答**：把多条命令打包**原子执行**（脚本期间单线程不中断）。用于分布式锁解锁、限流令牌桶、复杂原子操作。`EVAL`/`EVALSHA`。注意脚本不能太长（阻塞）。

---

### Q40. Pipeline 是什么？和事务区别？

**要点速答**：Pipeline 把多条命令打包一次发送，**省 RTT 提吞吐**，但不保证原子（中间可插别的命令）。事务保证顺序执行但不回滚。Pipeline 适合大批量无依赖命令。

## 十、对比与进阶

### Q41. Redis vs MySQL 缓存？

**要点速答**：Redis 内存极快做缓存/快取，MySQL 磁盘做持久主存。典型 Cache Aside：读先 Redis 未命中查 MySQL 回填；写先 MySQL 后删 Redis。Redis 不能替代 MySQL 的持久与事务。

---

### Q42. Redis vs ZK 分布式锁？

**要点速答**：Redis（Redisson）性能高、AP、偶发可能失效（主从切换丢锁）；ZK 基于会话+临时顺序节点，CP 强一致，锁更可靠但性能低。高并发容忍偶发选 Redis，强一致选 ZK/etcd。

---

### Q43. Redis 6.0 多线程是什么？

**要点速答**：6.0 网络 IO（读 socket、写 socket、协议解析/回写）可多线程并行，**命令执行仍单线程**。所以是"网络多线程 + 命令单线程"，提升网络 IO 瓶颈场景吞吐，不改变原子性。

---

### Q44. Redis 为什么不用多线程处理命令？

**要点速答**：命令执行单线程已够快（内存纳秒），多线程引入锁/切换/竞争复杂度，且 Redis 命令大多极短，瓶颈在网络 IO 而非 CPU。所以 6.0 只把网络 IO 多线程化，命令保持单线程简单原子。

---

### Q45. 热点 key 怎么处理？

**要点速答**：
1. **本地缓存**（JVM Caffeine）多级缓存。
2. **分片副本**：一个热点 key 拆成多个带后缀的 key 散到不同节点/槽。
3. 限流保护。
4. 监控发现热点（`hotkeys`）。

---

### Q46. Redis 内存碎片怎么产生和处理？

**要点速答**：频繁增删改导致分配的内存未满释放，产生碎片。用 `INFO memory` 看 `mem_fragmentation_ratio`。处理：重启（碎片整理）、4.0+ `activedefrag yes` 自动碎片整理、合理 expire 减少频繁变动。
