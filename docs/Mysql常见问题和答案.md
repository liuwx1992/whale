## 一、架构与存储引擎

### Q1. MySQL 一条 SQL 的执行流程？

**要点速答**：Client → 连接器（鉴权/线程）→ 查询缓存（8.0 移除）→ 解析器（词法语法→AST）→ 预处理器（表/列/权限）→ 优化器（选索引/Join 顺序）→ 执行器（调存储引擎接口取行）→ 返回。详见架构文档 §1。

---

### Q2. Server 层和存储引擎层的职责？

**要点速答**：Server 层跨引擎共享：连接/解析/预处理/优化/执行。存储引擎层决定数据存储、索引、事务、锁（InnoDB/MyISAM）。Server 通过 Handler API 调引擎。优化器选索引，但取数据由引擎干。

---

### Q3. InnoDB 和 MyISAM 区别？

**要点速答**：

| | InnoDB | MyISAM |
|---|---|---|
| 事务 | ACID | 不支持 |
| 锁 | 行锁+间隙锁 | 表锁 |
| 外键 | 支持 | 不支持 |
| 索引 | 聚簇+二级 | 非聚簇 |
| 崩溃恢复 | redo 支持 | 不支持 |

5.5+ 默认 InnoDB，生产基本只用它。

---

### Q4. MySQL 默认存储引擎是什么？为什么选 InnoDB？

**要点速答**：默认 InnoDB。因为支持事务、行锁高并发、崩溃恢复、外键，是 OLTP 主力。MyISAM 无事务、表锁并发差，基本淘汰。

## 二、索引

### Q5. 为什么 MySQL 索引用 B+ 树？

**要点速答**：B+ 树非叶子只存索引不存数据→单页键多→树矮→IO 少；叶子存全部数据且有序链表→范围查询极快。对比 B 树树高范围慢，哈希等值快但范围/排序不行。

---

### Q6. 聚簇索引和二级索引区别？

**要点速答**：
- **聚簇索引**：数据按主键顺序存在 B+ 树叶子，索引即数据，一张表一个，默认主键。
- **二级索引**：叶子存索引列+主键，查到主键后**回表**聚簇索引取完整行（除非覆盖索引）。

---

### Q7. 什么是覆盖索引？为什么快？

**要点速答**：查询字段全在二级索引叶子（含主键），**不用回表**，直接从索引返回。省一次聚簇索引 IO，快。`EXPLAIN Extra: Using index`。

---

### Q8. 联合索引最左前缀原则？

**要点速答**：联合索引 `(a,b,c)` 按 a→b→c 排序，查询必须从最左列开始才能走索引：`a`、`a,b`、`a,b,c` 走；`b,c` 无 a 不走（或退化）。范围查询右侧列失效（`a=? and b>? `后 c 用不到）。

---

### Q9. 索引失效的常见场景？

**要点速答**：
1. 函数/计算运算（`year(t)=2026`、`id+1=10`）。
2. 隐式类型转换（字符串列用数字查）。
3. 最左前缀缺失。
4. `like '%xx'` 左模糊。
5. `or` 两边不全有索引。
6. 范围列右侧。
7. `!=/not in` 视选择性。
8. 优化器成本判定全表更快。

---

### Q10. 索引下推 ICP 是什么？

**要点速答**：5.6+。二级索引取记录前，先在存储引擎层用 WHERE 中**索引列部分**过滤，减少回表次数。`Extra: Using index condition`。没 ICP 时先回表再过滤，慢。

---

### Q11. 唯一索引和普通索引性能差异？

**要点速答**：唯一索引插入要立即读页校验唯一性，**不能用 change buffer**，性能低于普通索引。读性能相近。除非业务要唯一约束，否则可只普通索引+业务校验。

---

### Q12. 主键为什么推荐自增？

**要点速答**：自增主键**顺序追加插入**，B+ 树叶子顺序写不分裂，写快不碎页。随机主键（如 UUID）插入导致页分裂、磁盘随机写、空间碎片。自增 bigint 是常规选择。

## 三、事务与隔离级别

### Q13. ACID 及保证机制？

**要点速答**：
- 原子性 → **Undo Log**（回滚）。
- 持久性 → **Redo Log**（崩溃恢复）。
- 隔离性 → **锁 + MVCC**。
- 一致性 → 上述三者 + 业务约束共同保证。

---

### Q14. 四种隔离级别？MySQL 默认哪个？

**要点速答**：

| 级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| RU 读未提交 | 有 | 有 | 有 |
| RC 读已提交 | 无 | 有 | 有 |
| **RR 可重复读（默认）** | 无 | 无 | 基本无 |
| Serializable | 无 | 无 | 无 |

MySQL 默认 **RR**。

---

### Q15. 脏读/不可重复读/幻读区别？

**要点速答**：
- **脏读**：读到别的事务**未提交**的修改。
- **不可重复读**：同一事务两次读同一行，值不同（被别人 update 提交）。
- **幻读**：同一事务两次范围查询，行数不同（被别人 insert 提交）。

---

### Q16. MySQL RR 怎么解决幻读？

**要点速答**：两方面：
- **快照读**（普通 select）：MVCC，读事务开始时快照，看不到后插入行。
- **当前读**（for update/update/delete）：**Next-Key Lock（行锁+间隙锁）** 锁住范围，阻止别的事务在范围内 insert。
基本解决幻读。特殊场景（先快照读后当前读混用）仍可能出现，需用 `for update` 加锁。

---

### Q17. 快照读和当前读区别？

**要点速答**：
- **快照读**：普通 select，读 MVCC 快照，不加锁。
- **当前读**：`select for update`、`update/delete/insert`，读最新已提交 + 加锁（行锁+间隙锁）。

---

## 四、MVCC 与锁

### Q18. MVCC 是什么？怎么实现？

**要点速答**：多版本并发控制，让读写互不阻塞。每行隐藏 `trx_id`+`roll_pointer`，多版本链在 undo log。读时用 **ReadView** 判可见版本。RC 每 select 新建 ReadView，RR 事务首次 select 建 ReadView 复用。

---

### Q19. ReadView 怎么判断版本可见性？

**要点速答**：ReadView 记活跃事务列表 `m_ids`、`min_trx_id`、`max_trx_id`、`creator_trx_id`。行 `trx_id`：`<min` 已提交可见；`>=max` 未来不可见；在区间内且在 m_ids 活跃不可见→找旧版本；在区间内不在 m_ids 已提交可见。详见架构文档 §5.2。

---

### Q20. InnoDB 行锁是加在什么上的？

**要点速答**：**加在索引上**。走索引才加行锁；不走索引（全表扫）会锁所有行/间隙，相当于表锁。所以更新务必走索引。

---

### Q21. Record/Gap/Next-Key Lock 区别？

**要点速答**：
- **Record Lock**：锁单行记录。
- **Gap Lock**：锁一段间隙（不含记录），防 insert。
- **Next-Key Lock**：Record+Gap，锁左开右闭区间，RR 当前读默认用它解决幻读。

---

### Q22. 死锁怎么产生的？怎么处理？

**要点速答**：两事务循环等待对方锁。InnoDB **死锁检测**（`innodb_deadlock_detect`）发现后回滚代价小的一方。处理：走索引、固定加锁顺序、拆小事务、设 `innodb_lock_wait_timeout`。

---

### Q23. 乐观锁/悲观锁？

**要点速答**：
- **悲观锁**：`select ... for update` 先加锁再操作。
- **乐观锁**：加 `version` 字段，更新时 `where id=? and version=?`，失败重试。读多写少用乐观，写竞争强用悲观。

---

## 五、日志体系

### Q24. MySQL 三大日志？

**要点速答**：
- **Redo Log**（InnoDB）：物理日志，崩溃恢复，WAL 顺序写，循环写。
- **Undo Log**（InnoDB）：回滚 + MVCC 旧版本。
- **Binlog**（Server）：逻辑日志，主从复制 + 归档恢复，追加写。

---

### Q25. Redo Log 和 Binlog 区别？

**要点速答**：

| | Redo Log | Binlog |
|---|---|---|
| 归属 | InnoDB | Server |
| 内容 | 物理页改 | 逻辑行变更 |
| 写法 | 固定循环 | 追加切文件 |
| 用途 | 崩溃恢复 | 主从复制+归档 |

---

### Q26. 什么是 WAL？

**要点速答**：Write-Ahead Logging。先写 redo log（顺序写快）再改 Buffer Pool（随机写慢）。commit 时 redo 落盘保证持久，脏页后台异步刷盘。崩溃后靠 redo 恢复已提交未刷盘的数据。

---

### Q27. 两阶段提交是什么？为什么需要？

**要点速答**：`redo prepare → binlog → redo commit`。保证 redo 与 binlog 一致，否则主从数据不一致。崩溃恢复时按两份日志状态对账：redo prepare 但 binlog 没写→回滚；都写了→提交。详见架构文档 §7.4。

---

### Q28. Binlog 三种格式？

**要点速答**：
- **Statement**：记 SQL，小但非确定函数（now/uuid）主从不一致。
- **Row**：记行的变更前/后值，精确但大，主从一致好，生产常用。
- **Mixed**：混合。推荐 Row。

---

## 六、Buffer Pool 与内存

### Q29. Buffer Pool 是什么？LRU 怎么改进？

**要点速答**：InnoDB 数据/索引页内存缓存，读写都先走它。LRU 改进：分 **young + old 区**，新页先入 old，被二次访问才升 young，防全表扫一次性污染 young。脏页后台异步刷盘，靠 redo 保证不丢。

---

### Q30. Change Buffer 是什么？

**要点速答**：二级索引页不在 Buffer Pool 时，写先记 change buffer 不立即读盘，后台/读时 merge，减少随机 IO。**仅非唯一二级索引**有效（唯一索引要立即读页校验）。

---

### Q31. Doublewrite Buffer 作用？

**要点速答**：防**页撕裂**。写页前先写双写缓冲（连续两份），若写一半崩溃，可从双写缓冲恢复完整页再用 redo。以小量写换可靠性。

---

### Q32. Adaptive Hash Index 是什么？

**要点速答**：InnoDB 监控热点查询自动为 B+ 树建内存哈希索引，加速等值查。争用大时可关（`innodb_adaptive_hash_index=off`）。

---

## 七、主从复制

### Q33. MySQL 主从复制原理？

**要点速答**：Master 写 binlog → Slave IO 线程拉取写 relay log → Slave SQL 线程回放 relay log → 数据同步。异步复制可能丢，半同步等 Slave 收到 binlog 才返回，MGR 组复制用 Paxos 强一致。

---

### Q34. 主从延迟原因和解决？

**要点速答**：原因：单 SQL 线程回放慢、大事务、Master 高并发。解决：**多线程复制（MTS，按库/行并行）**、拆小事务、Slave 提升硬件、读写分离走从库时容忍或读主。

---

### Q35. 异步/半同步/组复制区别？

**要点速答**：
- **异步**：Master 不等 Slave，性能高，可能丢。
- **半同步**：等至少一个 Slave 收到 binlog。
- **组复制 MGR**：Paxos 强一致，多主写入。

## 八、性能优化

### Q36. EXPLAIN 关键字段？

**要点速答**：
- `type`：访问类型 const > eq_ref > ref > range > index > ALL。
- `key`：实际索引。
- `rows`：估算扫描行数。
- `Extra`：Using index（覆盖）/ filesort（额外排序）/ temporary（临时表）/ index condition（ICP）。

---

### Q37. 慢查询怎么排查？

**要点速答**：开 `slow_query_log` + `long_query_time` 阈值 → 用 `EXPLAIN` 看执行计划 → 看是否走索引/扫描行数/Extra → 加索引/改 SQL/拆表优化。

---

### Q38. 深分页 `limit 100000,10` 慢怎么办？

**要点速答**：`limit M,N` 要扫 M+N 行，M 越大越慢。方案：
1. **延迟关联**：`select * from t join (select id from t where ... order by id limit 100000,10) x on t.id=x.id`，先走覆盖索引取 id 再回表。
2. **游标/标记**：`where id > last_id order by id limit 10`，翻页带上一页末尾 id。
3. 业务限制翻页深度。

---

### Q39. 大事务为什么有害？

**要点速答**：长事务持锁久阻塞并发、undo log 膨胀（MVCC 旧版本不能回收）、主从延迟、回滚段大。应拆小事务、避免长连接中的事务。

---

### Q40. 批量插入优化？

**要点速答**：
1. 批量 `insert ... values(...),(...)` 一条多行。
2. 自增主键顺序插避免页分裂。
3. 导入期临时关唯一校验/外键。
4. 大表用 `load data` 比 insert 快。
5. 合理事务分批 commit。

---

## 九、对比与选型

### Q41. MySQL vs MongoDB？

**要点速答**：MySQL 关系型+SQL+ACID+join，结构化业务主存。MongoDB 文档型+灵活 schema+水平扩展，半结构化、schema 频变。强事务多表选 MySQL，灵活文档大扩展选 Mongo。

---

### Q42. MySQL 索引 vs ES 倒排？

**要点速答**：MySQL B+ 树适合精确/范围/排序，`like '%xx'` 全表慢。ES 倒排适合全文检索/模糊/分词/聚合。常组合：MySQL 主存 + ES 搜索副本。

---

### Q43. 关系型为什么要分库分表？

**要点速答**：单表数据量大（千万级+）查询慢、单库容量/连接/IO 到瓶颈、写并发锁竞争。水平分表（按 sharding key 拆表）、垂直分库（按业务拆库）。代价：跨库 join/事务难、分布式 ID/路由复杂（用 ShardingSphere/MyCat）。

## 十、进阶追问

### Q44. count(*) / count(1) / count(列) 区别？

**要点速答**：`count(*)` 和 `count(1)` 不取值只计数，InnoDB 优化器选最小索引扫描，结果相同（含 NULL 行）。`count(列)` 只统计该列非 NULL 行数，需取值判断 NULL。`count(*)` 性能最优，推荐。

---

### Q45. InnoDB 一页多大？B+ 树为什么矮？

**要点速答**：默认页 16KB。非叶子只存主键+指针，一页能放上千键，3 层 B+ 树能索引千万级行。叶子存数据，三层 = 3 次 IO，配合 Buffer Pool 多在内存，查询极快。

---

### Q46. 自增 ID 用完了怎么办？

**要点速答**：自增 ID 有上限（int 21 亿、bigint 巨大）。int 用完插入报错。生产用 bigint unsigned 避免耗尽。若已耗尽需迁移到更大类型或分布式 ID（雪花）。

---

### Q47. 为什么不建议 select *？

**要点速答**：
1. 破坏覆盖索引（多取列导致回表）。
2. 传输多余数据。
3. 表结构变（加列）可能影响代码。
4. 优化器难选最优索引。明确列名。

---

### Q48. redo log 满了会怎样？

**要点速答**：redo log 固定大小循环写，write pos 追 check point。满了（write pos 追上 check point）会**暂停写，强制刷脏页推进 check point**，写性能下降抖动。生产调大 redo 文件+组避免频繁刷盘。

---

### Q49. online DDL 怎么做到不锁表？

**要点速答**：5.6+ Online DDL：建立新表/索引时在原表上加 MDL 写锁极短（建表/索引副本期间允许 DML 写 redo 同步到副本），完成后切换。重度 DDL 用 pt-online-schema-change / gh-ost（基于 binlog）更稳。

---

### Q50. 唯一索引冲突怎么处理？`insert ... on duplicate key` 原理？

**要点速答**：`ON DUPLICATE KEY UPDATE`：唯一键冲突时不报错，改执行 UPDATE（墓碑旧+写新的两步）。本质是 insert 失败转 update。注意可能导致主从不一致（statement 格式），生产慎用或用 Row 格式。
