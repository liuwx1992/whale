# MySQL 整体架构和深入理解

> **文档版本**: v1.0

> **编写人**: weixin.liu
> **用途**: 从整体架构到存储引擎/索引/事务/锁/日志/MVCC 全面拆解 MySQL（以 InnoDB 为主），供后续大模型阅读与排障

---

## 0. 一句话定位

MySQL 是一个**关系型、ACID 事务、存储引擎可插拔**的数据库。其架构经典在"Server 层（连接/解析/优化/执行）+ 存储引擎层（InnoDB/MyISAM）"分离，真正决定数据存储、索引、事务、锁的是**存储引擎层**（默认 InnoDB）。

---

## 1. 整体架构总览（一条 SQL 的旅程）

```
Client
  │  连接(连接池/线程)
  ▼
┌───────────────────────────────────────── Server 层 ─────────────────────────────────────────┐
│  连接管理 / 长连接 / show processlist                                                          │
│        │                                                                                       │
│  查询缓存(Query Cache, 8.0 已移除)                                                             │
│        │                                                                                       │
│  解析器(Parser): 词法+语法分析 -> 解析树(AST)                                                   │
│        │                                                                                       │
│  预处理器(Preprocessor): 检查表/列/权限                                                        │
│        │                                                                                       │
│  优化器(Optimizer): 选择索引/Join 顺序/生成执行计划(基于成本)                                    │
│        │                                                                                       │
│  执行器(Executor): 调存储引擎接口, 迭代取行                                                     │
└────────│───────────────────────────────────────────────────────────────────────────────────────┘
         │  读写接口(handler API)
         ▼
┌─────────────────────────────────────────────────────────────────────────────────────────────┐
│                                       存储引擎层(InnoDB)                                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐                                       │
│  │ Buffer   │  │  Undo Log│  │ Redo Log│  │  索引    │                                       │
│  │  Pool    │  │ (回滚/MVCC)│ │ (崩溃恢复)│ │ B+ 树   │                                       │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘                                       │
│         数据文件 .ibd / 系统表空间 / 双写缓冲 / change buffer                                  │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

Server 层（跨引擎共享）：
| 组件 | 职责 |
|---|---|
| 连接器 | 管理 client 连接与线程，鉴权，长连接复用 |
| 解析器 | 词法+语法分析，生成解析树 |
| 预处理器 | 检查表/列是否存在、权限 |
| 优化器 | 基于成本选择索引、Join 顺序，生成执行计划 |
| 执行器 | 调存储引擎接口，逐行取数据返回 client |

存储引擎层（InnoDB 核心）：
| 组件 | 职责 |
|---|---|
| **Buffer Pool** | 内存缓冲池，数据页/索引页缓存，读写先走这里 |
| **Redo Log** | 重做日志，保证崩溃恢复（持久性） |
| **Undo Log** | 回滚日志，保证事务回滚 + MVCC（一致性） |
| **B+ 树索引** | 聚簇索引 + 二级索引 |
| **Change Buffer** | 二级索引写优化缓冲 |
| **Doublewrite Buffer** | 双写缓冲，防页撕裂 |

## 2. 存储引擎：InnoDB vs MyISAM

| 维度 | InnoDB | MyISAM |
|---|---|---|
| 事务 | 支持 ACID | 不支持 |
| 锁粒度 | 行锁（+间隙锁） | 表锁 |
| 外键 | 支持 | 不支持 |
| 索引 | 聚簇+二级，B+ 树 | 非聚簇，B+ 树 |
| 崩溃恢复 | 支持（redo） | 不支持 |
| 全文索引 | 5.6+ 支持 | 支持 |
| 适用 | OLTP 主力 | 只读/统计历史（基本淘汰） |

MySQL 5.5+ 默认 InnoDB，生产基本只用 InnoDB。

## 3. 索引（InnoDB 的性能命脉）

### 3.1 B+ 树为什么是 B+

- **非叶子节点只存索引键**，不存数据 → 单页能放更多键 → 树更矮 → IO 少。
- **叶子节点存全部数据**，且**有序链表相连** → 范围查询顺链扫，极快。
- 对比 B 树：B 树每个节点都存数据，树高、范围扫慢；哈希：等值快但范围/排序不行。

### 3.2 聚簇索引 vs 二级索引

- **聚簇索引（Clustered）**：**数据按主键顺序存在 B+ 树叶子节点**，即"索引即数据"。一张表只有一个，默认主键。
- **二级索引（Secondary）**：叶子存"索引列值 + 主键值"。查二级索引拿到主键，再**回表**查聚簇索引拿完整行。

```
聚簇索引(主键):  叶子 = [完整行数据]
二级索引(普通):  叶子 = [索引列 + 主键]
  查二级索引 -> 拿主键 -> 回表聚簇索引取行 (除非覆盖索引)
```

### 3.3 覆盖索引

若查询字段都在二级索引的叶子（含主键），**不用回表**，直接从索引返回——覆盖索引。`EXPLAIN` 的 `Extra: Using index`。

### 3.4 联合索引与最左前缀

联合索引 `(a,b,c)`：
- B+ 树按 a→b→c 排序。
- **最左前缀**：能用索引的前提是查询条件从最左列开始。`a`、`a,b`、`a,b,c` 走；`b,c`（无 a）不走联合索引（可能走全索引扫）。
- 范围列右侧失效：`a=? and b>? and c=?`，c 用不到索引（b 范围后 c 无序）。

### 3.5 索引下推 ICP（Index Condition Pushdown）

5.6+ 引入。二级索引取出满足"用到索引列"的记录前，先在存储引擎层用 WHERE 条件中**索引列部分**过滤，减少回表次数。`Extra: Using index condition`。

### 3.6 哪些情况索引失效

- 函数/计算运算：`where year(time)=2026`、`where id+1=10`。
- 隐式类型转换：字符串列 `where phone=13800138000`（数字）。
- 最左前缀缺失。
- 范围后列失效。
- `like '%xx'` 左模糊。
- `or` 两边不全有索引。
- `!=`/`not in`/`is null` 视选择性可能不走。
- 优化器认为全表扫更快（小表或选择性差）。

## 4. 事务与 ACID

### 4.1 ACID

| 特性 | 保证机制 |
|---|---|
| 原子性 Atomicity | **Undo Log**（回滚未提交修改） |
| 持久性 Durability | **Redo Log**（崩溃恢复已提交） |
| 隔离性 Isolation | **锁 + MVCC** |
| 一致性 Consistency | 上述三者共同保证（业务约束） |

### 4.2 隔离级别

| 级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 RU | 有 | 有 | 有 |
| 读已提交 RC | 无 | 有 | 有 |
| 可重复读 RR（MySQL 默认） | 无 | 无 | 基本无（MVCC+间隙锁） |
| 串行化 Serializable | 无 | 无 | 无 |

**MySQL 默认 RR**，靠 **MVCC（快照读）+ 间隙锁（当前读）** 在 RR 下基本解决幻读。

### 4.3 快照读 vs 当前读

- **快照读**：普通 `select`，读 MVCC 快照，不加锁。
- **当前读**：`select ... for update`、`update/delete/insert`，读最新已提交数据，加锁（行锁+间隙锁）。

## 5. MVCC（多版本并发控制）

### 5.1 核心机制

每行隐藏两列：`trx_id`（最近修改事务ID）、`roll_pointer`（指向 undo log 旧版本）。每行可能存在**多个历史版本链**（undo log 链表）。

读时根据**读视图 ReadView**决定看哪个版本：
- RC：**每次 select 都生成新 ReadView** → 看到最新已提交 → 不可重复读。
- RR：**事务第一次 select 生成 ReadView 后复用** → 整个事务看同一快照 → 可重复读。

### 5.2 ReadView 判断可见性

ReadView 记录：`m_ids`（活跃事务列表）、`min_trx_id`、`max_trx_id`、`creator_trx_id`。比较行 `trx_id`：
- `< min`：已提交，可见。
- `>= max`：未来事务，不可见。
- 在 [min,max) 且在 m_ids 中：活跃，不可见 → 沿 roll_pointer 找旧版本重判。
- 在区间但不在 m_ids：已提交，可见。

### 5.3 MVCC 解决什么

让**读写不互相阻塞**：读走快照，写加行锁。RR 下快照读不阻塞写、写不阻塞快照读，大幅提并发。

## 6. 锁

### 6.1 锁分类

- **全局锁**：整库只读（FTWRL），备份用。
- **表锁**：`lock tables`、MDL（元数据锁，防 DDL/DML 冲突）、自增锁（AUTO-INC）。
- **行锁**（InnoDB 核心）：** Record 行记录锁、Gap 间隙锁、Next-Key Lock（Record+Gap）**。

### 6.2 行锁是加在索引上的

**关键**：InnoDB 行锁基于索引，**走索引才加行锁，不走索引会升级为表锁**（实际是锁所有行/间隙）。所以更新务必走索引。

### 6.3 间隙锁与幻读

RR 下当前读用 **Next-Key Lock（行锁+间隙锁）** 锁住一段范围，阻止其他事务在范围内插入，解决幻读。RC 没有间隙锁。

### 6.4 共享锁 S / 排他锁 X

- S（`lock in share mode`）：读锁，可并存。
- X（`for update`）：写锁，互斥。

### 6.5 死锁

两个事务互相等待对方锁。InnoDB 有**死锁检测**（`innodb_deadlock_detect`），发现后回滚代价小的一方。也可设锁超时 `innodb_lock_wait_timeout`。

## 7. 日志体系（高频核心）

### 7.1 三大日志

| 日志 | 位置 | 作用 |
|---|---|---|
| **Redo Log（重做日志）** | InnoDB 引擎 | 崩溃恢复已提交事务，保证持久性。WAL 顺序写 |
| **Undo Log（回滚日志）** | InnoDB 引擎 | 事务回滚 + MVCC 旧版本，保证原子性+一致性 |
| **Binlog（归档日志）** | Server 层 | 主从复制 + 数据恢复。逻辑日志 |

### 7.2 Redo Log 的 WAL 与两阶段

- **WAL（Write-Ahead Logging）**：先写 redo log（顺序写，快），再改 Buffer Pool（随机写，慢）。commit 时先写 redo 落盘，保证持久。
- **两阶段提交（2PC）**：保证 redo 与 binlog 一致：`写 redo(prepare) → 写 binlog → 写 redo(commit)`。崩溃恢复时按 redo/binlog 状态决定提交或回滚。

### 7.3 Redo vs Binlog

| | Redo Log | Binlog |
|---|---|---|
| 归属 | InnoDB 引擎 | Server 层 |
| 内容 | 物理日志（页的物理改） | 逻辑日志（行的 SQL 变更） |
| 大小 | 固定循环写 | 追加写，写满切新文件 |
| 用途 | 崩溃恢复 | 主从复制、归档恢复 |

### 7.4 为什么需要两阶段提交

要让 redo 和 binlog 一致，否则主从数据不一致。redo prepare → binlog → redo commit，任何阶段崩溃都能靠两份日志对账恢复。

## 8. Buffer Pool 与 change buffer

### 8.1 Buffer Pool

InnoDB 把**数据页/索引页**缓存在内存（Buffer Pool），读写都先走这里。基于 LRU 变种（**改进版 LRU**：young + old 区，新页先入 old 防全表扫污染 young）。

脏页由**后台刷盘**（异步），靠 redo 保证不丢。

### 8.2 Change Buffer

二级索引页不在 Buffer Pool 时，写操作先记 change buffer（不立即读盘），后续读或后台 merge。减少随机 IO。仅对**非唯一二级索引**有效（唯一索引要立即读盘校验）。

### 8.3 Doublewrite Buffer

写页前先写双写缓冲（连续两份），防止**页撕裂**（partial page write，写一半崩溃）。崩溃后从双写缓冲恢复完整页再用 redo。

### 8.4 Adaptive Hash Index

InnoDB 自动监控热点查询，为 B+ 树建内存哈希索引加速等值查。监控/争用大时可关。

## 9. 主从复制

```
Master 写 binlog -> Slave IO 线程拉取 -> 写 relay log -> Slave SQL 线程回放 relay log -> 数据同步
```

- 异步复制：Master 不等 Slave，性能高可能丢。
- 半同步复制：Master 等至少一个 Slave 收到 binlog 才返回。
- 组复制 MGR：基于 Paxos 强一致。

主从延迟：单 SQL 线程回放慢 → 多线程复制（MTS，按库/按行并行）。

## 10. SQL 执行与优化

### 10.1 优化器选择索引的依据

- 基于成本（cost）：扫描行数估算 + 顺序读/随机读成本。可能选非预期索引。
- 可用 `force index` 强制。`EXPLAIN` 看执行计划。

### 10.2 EXPLAIN 关键字段

| 字段 | 含义 |
|---|---|
| type | 访问类型：const > eq_ref > ref > range > index > ALL |
| key | 实际用的索引 |
| rows | 估算扫描行数 |
| Extra | Using index（覆盖）/ Using filesort（额外排序）/ Using temporary（临时表）/ Using index condition（ICP） |

### 10.3 索引优化原则

- 查询条件走联合索引最左前缀。
- 高选择性列建索引。
- 覆盖索引减少回表。
- 范围查询放联合索引最后。
- 避免函数/计算/隐式转换导致失效。
- 长字符串用前缀索引。

## 11. 性能与运维要点

| 关注点 | 做法 |
|---|---|
| 索引 | 联合最左、覆盖、避免失效 |
| Buffer Pool | 给足内存（物理 50~70%） |
| 隔离级别 | 默认 RR，必要时 RC |
| 大事务 | 拆小，减少锁持有与 undo 膨胀 |
| 死锁 | 走索引、固定加锁顺序、开检测 |
| limit 深分页 | `where id>last_id limit n` 延迟关联 |
| 插入 | 批量 insert、自增主键顺序插、关唯一校验 |
| redo | 调大 redo 文件/缓冲提写吞吐 |
| binlog | row 格式（精确）+ 合理保留期 |
| 慢查询 | 开 slow log + EXPLAIN 分析 |
| 表设计 | 字段合适类型、避免大字段在主表（拆表） |

## 12. 一张图串起核心概念

```
Server 层: 连接 -> 解析 -> 预处理 -> 优化器(选索引) -> 执行器 -> 引擎接口
InnoDB: Buffer Pool(LRU) <-> B+树(聚簇=数据, 二级=主键回表, 覆盖免回表)
事务: ACID = Undo(原子+MVCC) + Redo(持久WAL) + 锁/MVCC(隔离)
       RR: 快照读(MVCC ReadView) + 当前读(行锁+间隙锁 Next-Key)
日志: Redo(引擎物理/崩溃恢复) + Undo(引擎回滚) + Binlog(Server逻辑/主从)
       两阶段提交: redo prepare -> binlog -> redo commit
复制: Master binlog -> Slave IO(relay) -> SQL 回放
```

记住这条链，就抓住 MySQL 全部骨架：**Server/引擎分层、B+ 树索引、MVCC、Undo+Redo+Binlog 两阶段、锁、主从**。
